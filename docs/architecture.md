# Architecture

## Phase 5 evidence graph

`client/graph/` converts the existing `AnalysisReport` and in-browser reviewed text into a typed graph. This is a pure client transformation; no graph endpoint, database, provider call, or new risk calculation exists. The fictional landing-page `EvidenceGraph` stays separate. The report and graph are two views over the same validated API response.

The six node types are `OPPORTUNITY`, `CLAIM`, `EVIDENCE`, `RISK_FINDING`, `UNCERTAINTY`, and `VERIFICATION_ACTION`. The contract also defines `CONTAINS`, `SUPPORTS`, `INDICATES`, `REQUIRES_VERIFICATION`, `REMAINS_UNCONFIRMED`, and `ADDRESSES` relationship types. The current builder emits only relationships justified by the report: exact source evidence supports claims or findings; findings indicate warning signs for the opportunity; claims and uncertainty remain unconfirmed; recommended actions request independent verification of the opportunity. It deliberately emits no `ADDRESSES` edge because the server contract does not associate actions with specific findings. There is no causation or independent-verification edge.

The builder preserves finding IDs, validates exact quotation/offset pairs against reviewed text, deduplicates evidence by span and origin, and discards malformed spans. Node IDs derive from the analysis ID, finding ID, or source offset/content. Edges require both endpoints and are deduplicated. The opportunity node uses a neutral title; the model's opportunity category is shown only as an AI category in the inspector. User-reviewed OCR and URL text retain their extraction origin but never become verified facts. Labels are React text nodes; no model output is parsed as HTML or used for navigation. The original extracted text remains visible above the review form, separate from the reviewed text used by the graph and source highlight.

The visual layer uses native React buttons and SVG paths rather than React Flow. The report is capped at 12 model findings and claims, so fixed horizontal lanes with 148 px row slots yield stable nonoverlapping node positions with no layout engine. Shared evidence may produce crossing connections, but duplicate evidence is shown once. The first eight matching nodes appear by default, with a show-all control for larger reports. Filters retain supporting evidence and the opportunity when relevant. A structured, keyboard-accessible list exposes every node even when the canvas is collapsed. The graph component is loaded lazily after analysis; native buttons handle selection, source tracing, zoom, fit, and reset, while pointer dragging pans empty canvas. The inspector stacks below the canvas on narrow screens. No dependency or backend memory cost is added. The local production build produces a separate graph chunk of 11.77 KB JavaScript (3.76 KB gzip) and 7.49 KB CSS (1.90 KB gzip); its small report integration also increases the main bundle. The built app was inspected in local Chromium at 1440, 1280, 768, and 390 CSS-pixel widths, with no horizontal page overflow and working touch pan. Actual Embarko behavior remains unverified.

## Phase 4 analysis path

After intake, the browser retains the original extraction and presents an editable copy. The user can inspect extraction notes and a local screenshot preview, correct OCR, remove personal data, and explicitly submit the confirmed text. Only `reviewedText` goes to Groq; this can equal the original extraction when left unchanged. File bytes are not sent. The browser receives a report only after server-side validation. `POST /api/analyze` is separate from extraction and does not start an OCR or PDF worker.

The Node handler validates the request with Zod, limits the JSON body to 50 KB, allows two concurrent analyses and six requests per IP per minute, and calls the Groq chat completions REST endpoint. The default `openai/gpt-oss-120b` supports strict JSON schema output in [Groq's current documentation](https://console.groq.com/docs/structured-outputs). `GROQ_MODEL` overrides it. The server uses an 18-second total deadline, at most one retry on transient provider/network errors, and a 2,500 completion-token cap. Authentication, model, rate, network, timeout, and malformed-output failures return sanitized JSON. There is no synthetic fallback analysis. Secrets stay in server environment variables and request headers; source text, model responses, and keys are not logged.

The model's output is parsed by a strict Zod schema. Each claim and finding quotation must occur in the reviewed text with only whitespace differences allowed. A narrow model quote is expanded to its exact surrounding source sentence before a conservative category-specific lexical check. The validator records offsets, removes invented or unsupported quotes, and deduplicates a category plus quotation pair. It also excludes instruction-like source text from the claims list. Model-written summaries, claim labels, and finding explanations are discarded; the API creates these from retained evidence and fixed cautious wording. The lexical check is a guard against obvious mismatches, not a proof of semantic correctness. Reported extraction provenance is client-supplied, so `provenanceAuthenticated` is false. The model has no tools or independent research. The report calls source claims observed text, findings AI interpretations, and independent verification absent.

The warning-sign index is deterministic. Category base weights: payment 28, urgency 16, personal information 22, identity 15, channel 9, compensation 8, verification avoidance 20, link 14, contradiction 15, other 8. Severity multiplies by 0.5/0.75/1 for low/medium/high. Uncertainty multiplies by 1/0.7/0.4 for low/medium/high. Each category contributes only its strongest validated finding. The rounded total is capped at 100. Thresholds: 0–19 limited warning signs, 20–39 caution advised, 40–64 elevated risk, 65–100 high risk. No supported findings, fewer than 50 source characters, or only high-uncertainty findings yields **Inconclusive** regardless of score. This index is a heuristic warning-sign count, never a probability of fraud or legitimacy. OCR-derived quotations containing digits or currency are forced to high uncertainty even when the user edits the text; edits do not establish factual accuracy. Reports from OCR always carry a deterministic limitation reminding users to compare the original screenshot.

The API does not persist cases. UUIDs and extraction method fields supplied by the browser are references, not authenticated proof of intake. The screenshot preview is a local object URL. Stronger abuse prevention and target-host memory checks remain deployment tasks. The 256 MB hosting budget remains unverified with Groq analysis plus the built app.

## Current shape

ProofPath is one npm package. React, strict TypeScript, Vite, and Tailwind power the editorial landing page and `/verify` workspace. A native Node HTTP server serves the built app and exposes `/api/health` and `POST /api/intake`. Shared transport types live in `shared/`; Zod validates JSON source shape, processed receipts, and server configuration. Vitest covers API and frontend behavior.

```text
Browser → Vite (development) → React /verify → /api proxy → Node intake
Browser → Node (production) → built React + intake API
```

The Node process uses `PORT` and binds to `0.0.0.0` for deployment. It needs no database, queue, external API, or container. Embarko build/start settings can use `npm run build` and `npm start`, subject to the platform's current requirements.

## Intake flow

1. The client selects one of four source types, validates basic shape and limits, and submits to `/api/intake`.
2. Text and URL requests use JSON. File requests send raw bytes with source type and encoded filename headers. This avoids an additional multipart dependency.
3. The server checks content type, body size, source schema, and file signature, then dispatches to `server/processing/`. Text is conservatively normalized; URL retrieval is guarded; image pixels are fully decoded and OCR runs in a bounded child process; PDF text uses a separate bounded child process.
4. The response includes an unpredictable UUID case ID, UTC timestamp, source metadata, available text, processing status, extraction method, provenance, and warnings. No risk claim is generated.

The server does not persist source content or log submitted text or bytes. Case IDs are response identifiers only; there is no lookup API. The browser retains input while editing and clears it when starting a new case.

## Security and resource boundaries

- URL retrieval uses Node HTTP(S) with no browser, JavaScript execution, credentials, cookies, or external AI API. It rejects IP literals, local names, unusual ports, private/reserved DNS answers, and mixed public/private DNS sets. Each hop resolves again and connects to the validated IP through a pinned lookup; TLS keeps the original hostname for SNI and certificate checks. Redirects are capped at 3. DNS/total retrieval has an 8-second deadline, connection idle timeout is 3 seconds, response headers are limited to 16 KB, encoded bodies to 1 MB, and decoded bodies to 2 MB. Only UTF-8/ASCII HTML or plain text is processed. Network and format failures produce an unavailable receipt, while unsafe destinations are rejected. Outbound egress filtering remains recommended as defense in depth.
- Strict text and URL limits; binary size limits enforced from both `Content-Length` and streamed bytes; file signature inspection is independent of extension and MIME type.
- Filenames are URI decoded, reduced to the final path segment, stripped of control characters, and capped at 160 characters.
- A lightweight per-IP limit allows 12 intake requests per minute. The process allows two concurrent intakes and one heavy job (PDF or OCR) at a time. These limits are per process, not a distributed abuse control.
- PDF extraction runs in a child process with a 12-second timeout and 160 MB V8 old generation limit. Aborted requests terminate the child. PDFs are capped at 15 pages and 20,000 extracted characters. A native parser crash is isolated from the intake server. Page numbers with selectable text are recorded; blank pages in mixed documents produce partial warnings. Fully scanned PDFs still return an OCR-required error. The parser may briefly use additional native memory; deploy with a memory limit that accommodates the Node process and one PDF child.
- Image uploads are restricted to PNG/JPEG/WebP, 5 MB, and 12 megapixels before decoding. The isolated OCR child validates full pixel decoding with Sharp in strict mode, rotates by EXIF orientation, downsizes to at most 1,600 px on either side, and runs Tesseract.js 7 with the bundled English LSTM model. It has a 15-second timeout, 128 MB V8 old-generation limit, and a sampled 160 MiB RSS watchdog. Native memory is not constrained by the V8 limit, and the watchdog is not a hard OS memory cap; the deployment's process/container limit remains essential. The child exits after every job and writes no cache or temporary file.
- The HTTP server has 20-second request and 10-second headers timeouts. Failures return safe structured errors without stack traces. Intake responses use `Cache-Control: no-store`.
- No permanent storage is created. PDF and OCR children exit or are terminated after extraction, timeout, or abort.

`client/` must never contain API keys. Vite exposes `VITE_` variables to browsers, so server credentials must not use that prefix. Provenance distinguishes user-supplied, retrieved, extracted, and unavailable content; extraction does not establish authenticity. Phase 4 analysis is available only after the user confirms reviewed text.

## OCR decision

| Option                                   | Accuracy and languages                                                     | Runtime and deployment                                                                                     | Decision                       |
| ---------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Tesseract.js 7 with bundled English data | Good for clear printed text; weak on handwriting and some currency symbols | Offline core and language model; measured locally for the controlled screenshot                            | Selected, isolated per request |
| System Tesseract binary                  | Mature OCR with installed language packs                                   | Requires an OS binary and language files on Embarko; not portable in the current single-package deployment | Not selected                   |
| Hosted OCR service                       | Varies by provider                                                         | Sends private screenshots externally and requires credentials and network access                           | Not selected                   |

Screenshots return `image_ocr` text only after full decode and a successful OCR result. Blank or corrupt images return a structured 422 error. The controlled screenshot's title, numeric payment amount, deadline, and email were extracted; the rupee glyph was omitted by the English model. OCR is a transcription aid, not verified evidence. Fully scanned PDFs still report that OCR is required; reusing OCR on PDF pages would need bounded rendering and a separate memory evaluation.

After downsampling, local Windows/Node 22 measurements showed 1,059 ms and 112.2 MiB peak OCR child RSS for the controlled 1,200×280 screenshot. A 12-megapixel white image with a text label took 1,216 ms and reached 127.1 MiB worker RSS. The API process was observed around 75 MiB, so the larger sample implies roughly 202 MiB across API and one OCR child, excluding platform overhead and any concurrent text/URL request. These are sampled observations, not a proven worst case. [Embarko documents a 256 MB per-app limit](https://embarko.ai/guides/free-hosting-for-students); deployment-specific RSS and OCR accuracy still need verification. A controlled HTTPS fixture verifies pinned transport SNI and hostname rejection with a locally trusted test certificate. Its PEM key under `server/processing/fixtures/` is test-only and is never trusted by production requests. Public `https://example.com/` extraction succeeded when outbound network access was granted; sandboxed sockets returned `EACCES`.
